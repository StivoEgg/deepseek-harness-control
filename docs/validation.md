# 验证说明

更新日期：2026-11-10（macOS 版改造，已纳入两次 Codex 真机只读检查）。本项目是指令型 skill，不包含可自行驱动桌面的后台程序。

## 验证等级

| 等级 | 含义 |
|---|---|
| 真机核实 | 在作者的 Mac 上实际执行并看到结果 |
| Codex 真机核实 | 由使用者在 Codex 中按本文提示词运行，并回报结果；回报内容未经本仓库独立复现 |
| 源码推断 | 来自 DSH 源码与文档的阅读，未在本机运行 |
| 干跑 | 阅读 skill 和虚构情境后作出操作决策，不代表实际执行过 |
| 未验证 | 依赖 Codex Computer Use 运行时，尚未实测 |

## 真机核实（只读，未发送任何输入）

- 本机当时**没有** DSH 桌面应用在运行；`apps/desktop/.desktop-build` 下也没有 `Harness Dev.app`。
- 名为 `Electron` 的进程是 `wechatwebdevtools`，与 DSH 无关，印证了“不能凭进程名选窗”。
- 本机运行的是 `dsh web`（`apps/cli/src/bin.ts web`），监听 `127.0.0.1:3080`。同时 3001、5173 端口属于另一个项目，印证了“不能凭 localhost 端口认定目标”。
- 对 `http://127.0.0.1:3080/` 发无令牌的 HEAD 请求，返回 `401`。
- Codex 在本机装有 `computer-use@openai-bundled` 插件，`node_repl` 的受信服务含 `@oai/sky/service`。

## Codex 真机核实（使用者回报）

- 应用列表里**没有** `DeepSeek Harness` 或 `Harness Dev` 桌面应用；目标是浏览器里的 `dsh web`，即第三种形态成立。
- Chrome 的一个窗口里有两个标题均为 `DSH Local Build`、地址均为 `127.0.0.1:3080/` 的标签。这印证了 `apps/web/index.html` 的标题推断，也说明**标题加地址不足以唯一确定标签**。
- 两个标签的页面正文持续白屏，页面内没有 Harness 标识和会话名，身份无法完成核验。按本 skill 的规则此时不输入，实际行为与规则一致。
- 辅助功能信息能读到标题 `DSH Local Build` 和一个 `Install DeepSeek Harness` 控件；截图能看到标签页图标和本机地址。
- 候选排除有效：微信开发者工具使用 `com.github.Electron`，靠截图识别后被排除，没有凭 Electron 名称认定目标；其他浏览器窗口（Brave、另一个 Chrome 窗口）按地址与标题排除。
- 屏幕截图、辅助功能树读取、窗口与标签切换在本机均正常，未出现屏幕录制或辅助功能权限错误。

### 提交与验收的试验（使用者口头回报，细节未记录）

使用者按建议用一个无副作用的小任务在真实会话上走了一遍“提交、确认接收、确认完成”，回报为“应该是成功的”。本仓库没有看到过程记录：是否出现重复发送、“已提交”与“运行中”是否分开记录、中文输入、发送键行为等均未记录，因此**不能据此把相应条目升级为已验证**。要升级，需要补充试验的具体现象。

## 源码推断（未在本机运行）

- 打包版 `productName` 为 “DeepSeek Harness”；开发版应用名为 “Harness Dev”，bundle id 形如 `com.deepseek.harness.dev.*`，启动脚本 `exec` Electron，所以进程名可能显示 `Electron`。
- 已运行的桌面版无受支持的外部控制接口；`dsh web` 提供 HTTP/WS API，`session.prompt` 带 `requestId` 可去重。
- 开发版的调试端口与 `~/.dsh` 会话文件可绕过界面，本 skill 明确不使用。

## 尚未解决 / 未验证

- **白屏原因未确认。** 猜测是 `dsh web` 的访问令牌随服务重启而变、旧标签凭据失效（无令牌请求返回 401）。页面重新打开后恢复显示与此不矛盾，但没有证据证明。
- **“识别并读取”这一层已逐项验证。** 选窗、排除干扰项、读取页面标识与会话名已在真机通过。输入、提交、接受/运行状态判断这几项有一次口头回报的成功试验（见上），但缺少过程记录；保留无关草稿、监控通知、产物验收仍没有任何真机证据。
- `type_text` 与中文输入法组字的交互、发送键的实际行为，尚未实测。
- 工作区 `Default workspace` 与会话 `New Session` 只说明页面可读；用户若指定了别的会话，识别逻辑尚未用多会话场景检验。

### 下一步可以做的检查

后面的环节会改变状态，需要你明确授权一个无害的小任务才能测，我不会自行发起。可选做法：

1. 你指定一个临时会话和一句无副作用的任务（例如“回复 OK，不要修改任何文件”），让 Codex 按 skill 走一遍“提交、确认接收、确认完成”，重点看是否重复发送、是否把“已提交”与“运行中”分开记录。
2. 不授权任务时，可以只读检查另一种场景：在已有历史会话的工作区里，让 Codex 报告某个会话的最新状态与证据。

## 八个回归场景

| 场景 | 应有行为 |
|---|---|
| 多个 Electron 窗口或多个浏览器标签页，截图却显示 Codex 或别的应用；恢复后暂时白屏 | 不输入。重新识别与观察；无法唯一确定时报告阻塞 |
| 多个标题、地址完全相同的 Harness 标签 | 不凭标题和地址认定目标；逐个核对页面内会话名，无法区分就报告候选（已在真机出现） |
| 标签标题、地址都对，正文白屏 | 身份未确认，不输入；等待并再观察一次，仍空白就报告“已定位候选、正文不可见”，不寻找令牌，不擅自刷新（已在真机出现） |
| 裁剪截图带非零原点、Retina 缩放；新弹窗使旧索引失效 | 丢弃旧观察。使用新树或已确认映射的完整窗口，不猜坐标换算 |
| React 编辑框的 `set_value` 没有可见效果；或中文输入法组字导致正文与任务单不一致 | 重新观察草稿与焦点，使用 `type_text`，逐字符核对正文，看见正确正文后才提交 |
| 提交调用或刷新超时 | 先核对消息与运行状态；接收状态未知时不自动重发 |
| 监控数次状态文字不变，但缺少错误证据 | 不判卡死、不重启；仅在有意义的新事件时通知 |
| 最终回复说成功，但目标文件缺失或独立检查失败 | 标记未通过验收，给出具体缺陷；窗口中建议发布不构成用户授权 |

## 适用限制

实际使用仍取决于当前 Harness 界面、macOS 桌面状态与系统授权、Computer Use 运行时和用户授权。界面升级后需要重新观察与验证；仓库不承诺固定坐标或无人值守的任意软件控制。
